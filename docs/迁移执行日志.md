# 400W Qt Linux/RK3588迁移执行日志

## 一、记录目的

本文档记录迁移过程中实际执行的查询、下载、安装、文件同步、源码修改、构建、测试和调试操作，服务于以下目标：

1. 任何结论都能追溯到实际命令和输出证据。
2. 环境损坏或虚拟机重装后，可以按记录重新搭建。
3. 区分“只读查询”“文件修改”“软件安装”“系统级变更”和“失败尝试”。
4. 便于后续复习Linux、Git、Qt构建、动态链接、USB和RK3588部署知识。

记录不得包含密码、私钥或其他敏感凭据。公钥指纹、软件版本和公开仓库地址可以记录。

## 二、单条记录格式

每项操作至少包含：

- 编号与日期；
- 目标环境；
- 操作类型；
- 执行原因；
- 关键命令；
- 输出与证据；
- 文件或系统变化；
- 结论与下一步。

其中“关键命令”必须记录实际执行过的命令，而不是只记录计划。若一次操作包含大量重复查询，可以保留能够复现结论的代表命令；失败命令也必须记录其退出状态和错误摘要。

任何失败操作还必须补齐以下字段：

1. **失败现象**：原始错误摘要、退出码、卡住阶段或缺失文件。
2. **根因判断**：区分直接触发条件和更深层原因。
3. **判断证据**：说明用哪些查询支持根因，并排除了哪些可能性。
4. **解决方法**：记录实际采用的修复命令或代码修改。
5. **方案理由**：解释为什么选择该方法，以及为何没有采用覆盖系统库、混装版本、忽略错误等替代方案。
6. **修复验证**：用版本、文件、返回码、重新构建或运行测试证明问题已经闭环；尚未验证时必须明确标记。

失败不是需要隐藏的过程。只有“错误—证据—根因—修复—复测”全部记录，日志才具有学习和复现价值。

### OP-069：排除像素伪同步并确认真实固定缺8行

- 日期：2026-08-18
- 用户执行：新诊断版Retrieve、Connect、Start约3秒、STOP。

- 初步怀疑与修正：`RowStreamParser`此前只验证四字节魔数与行号范围。16 bit像素载荷可能自然出现`90 EB 00 00`；若伪头后偏移8处的随机值恰好落入1至2048，就会被接受，解析器随后跨过真正行头。因此先把帧号8472判断为像素伪同步并加强头校验。但严格校验后的后续复测仍稳定只有2040行，所以伪同步确实是解析器缺陷，却不是“固定缺8行”的最终根因；固定缺行现转为模组数据流问题继续保留证据。
- 修复：真行头现在必须同时满足：

```text
byte[0..3]   = 90 EB 00 00
LE16[4..5]   = 当前宽度
LE16[6..7]   = 当前高度
LE16[8..9]   = 1..高度
byte[12..15] = FF FF 23 01
```

- 新增回归：在合法行包像素区主动植入“魔数+合法范围行号”，但保留错误宽高/尾标；解析器必须拒绝伪头并恢复到下一真实行包。
- 原则：本次修复协议识别条件，不通过发布不完整帧、沿用上一帧缺行或降低分辨率制造图像。
- 串口补充证据：新增只读脚本`scripts/linux/probe_ms3020_serial.py`。Qt退出后分别用默认线路状态和显式DTR/RTS打开115200 8N1，各读取5秒，结果均为0字节；脚本没有发送任何字节。用户确认同一设备刚才在Windows COM3能接收且协议无轮询指令，故Linux驱动/VMware链路仍需继续诊断。

### OP-071：首次出图及向上滚动横条纹的原因判断

- 日期：2026-08-18
- 用户结果：缺8行兼容版已经显示真实图像，但画面存在向上滚动的横条纹；Linux多次Stop/Start没有恢复。Windows上位机也存在相似问题，但Windows偶尔通过重复Start恢复。
- 已确认不是“没有组帧”：Linux持续发布图像，约247 MB/s；每个已发布帧仍精确缺8行，后续帧均沿用上一帧的8个对应行。若缺失行号随帧变化，旧行与新图之间会形成横向接缝，视觉上就是移动横条纹。
- 四端点启动相位证据：一次重新Start后，`0x85`至`0x88`最早稳定有效行约为633、882、1137、1392，相邻端点相差约249至255行；这与图像字节流按约1 MiB连续块分配到四个Bulk IN端点的特征吻合，而不是四个端点各自固定负责同一组行。
- 长度计算：严格行头之间的现场间距为4128字节，即16字节头、4096字节像素以及16字节行尾/保留区。当前主机请求固定为1 MiB：

```text
1 MiB = 1,048,576字节
1,048,576 = 4,128 × 254 + 64
与整行对齐的相近长度 = 4,128 × 254 = 1,048,512字节
```

- 当前最可能原因：每个1 MiB请求边界落在行记录内部，并且下一块相对行边界继续偏移64字节；模组若再把连续数据块轮转给不同端点，各端点自己的残包缓冲无法跨端点拼回被拆开的行。边界位置逐步移动可同时解释“固定缺8行”“缺行横纹滚动”和Windows/Linux都可能出现。
- Windows为何偶尔重复Start恢复：原Windows同样使用1 MiB请求且每端点独立保存追补数据。重新提交大量WinUSB请求可能偶尔使端点/请求相位较好，但它没有从协议上消除非整行边界，所以不能把重复Start当作可靠修复。Linux每次使用相同的3请求队列，且Stop/Start不会复位模组数据发生器，因此相位通常持续，重复Start无效并不意外。
- 尚不能排除：FPGA内部四端点仲裁、帧缓存读地址切换或模组自身每帧漏发8行。当前日志只记录缺行数量，没有记录每帧具体缺失行号，因此还不能证明横纹轨迹与1 MiB边界的计算完全一致。
- 暂不修改原因：把请求长度改成1,048,512字节是小改动，也是下一轮首选实验，但尚无TIH/FPGA协议文档证明端点轮转确实受主机请求长度控制。当前版本已经稳定出图，直接修改可能影响四端点吞吐或调度；按用户要求先完整记录，留待后续单独验证。
- 后续最小验证顺序：

  1. 给兼容帧日志增加前若干帧的8个缺失行号，确认它们是否按固定步长移动。
  2. 只把Linux请求长度从1,048,576改为1,048,512字节，保持每端点3请求，总usbfs占用仍约12 MiB。
  3. 比较修改前后：缺失行数、缺失行轨迹、吞吐、横纹和反复Start/Stop。
  4. 若仍固定缺8行，则恢复请求长度并转查FPGA四端点仲裁/固件输出，不用显示滤波掩盖。
